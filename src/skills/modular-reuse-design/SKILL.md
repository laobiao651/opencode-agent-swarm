# 模块化与复用优先设计

## 核心哲学

**写代码前先看，再决定怎么做。**

新代码的存在必须有理由。如果项目里已有同等能力，调用它；如果有相邻能力，扩展它；只有确认无可复用、且不强行抽象时才新建。

但这不是教条——**API 粒度选择、模块边界划分本身没有绝对对错，关键是与项目既定模式一致**。

## 何时激活

**激活：**
- 新增函数、组件、类、模块、类型、工具、hook、service
- 任务措辞含"加一个 / 实现 / 支持 / 新增"
- 重构任务（重新评估模块边界）

**不激活：**
- 纯 typo / 文案修改
- 已知改点的 bug 修复（改动定位明确）
- 配置文件调整

## 三层扫描诊断

激活后必须输出这三层报告，缺一不可：

### L1 现成可直接调用（功能完全匹配）
扫描方法：grep 函数名/组件名同义词、查看类型定义、检查 service/util/hook 目录
判定：现有实现的输入输出与本次需求兼容
输出：路径:行号 + 名字
若 L1 命中 → 决策可定为"直接复用"，无需继续 L2/L3

### L2 同领域已有族成员（功能相邻）
判定：解决同类问题但具体能力不同（如 getUserName / getUserPhone / getUserEmail）
输出：
- 族成员列表
- 模式特征（细粒度专用 / 通用参数化 / 混合）
- 本次需求是否能加入该族

### L3 项目整体复用模式诊断
判定：跨领域观察项目设计风格
输出：
- 数据访问模式：DAO 细粒度方法 / 通用 query / Repository / 直 ORM
- 工具层模式：集中 utils/ / 按领域分散 / 第三方为主
- 组件层模式：通用组件库（Table/Form/Pagination 等）已有哪些
- 业务逻辑层模式：service / use-case / hook / 直接组件内

## 决策框架

四种决策，每种都要有依据：

| 决策 | 触发条件 | 风险 |
|---|---|---|
| **直接复用** | L1 命中且兼容 | 低，必选 |
| **遵循族模式** | L1 无、L2 命中、本次能加入族 | 低，与项目一致 |
| **扩展现有** | L1 接近但少几个能力（如加参数/选项） | 中，可能影响调用点 |
| **借机重构** | L2 命中但模式碎片化、本次是好契机 | 高，须问用户 |
| **确认新建** | L1/L2 都无，L3 模式允许新建该层 | 中，需明确理由 |

## 必须停下问用户的高风险决策

无论用户原话怎么说，命中下列任一就**停下问用户**，不直接派发实施：

- 决策影响 ≥3 个现有调用点（重构）
- 决策会改变项目既定的 API 粒度模式
- 决策涉及公共抽象提取或公共模块新设
- 决策涉及跨模块接口、权限模型、DB schema 变更
- 决策与现有模式冲突且无法收敛

提问模板：
```
本次任务发现 <现状描述>，有以下选项：
- A. <低风险方案，工作量 X>
- B. <借机重构，工作量 Y，影响 N 个调用点>
推荐 <A/B>，理由：<...>
请选择。
```

## 模块化设计原则

复用决策做完后，落到具体代码组织时遵循：

1. **按领域职责拆分**，不按文件数量或代码长度拆。一个 user-auth 模块 500 行可以是合理的；十个 user-helper-1 ~ user-helper-10 各 50 行通常是错的。

2. **单一职责 + 稳定接口**：模块对外暴露的接口要稳定，内部实现可以演化。

3. **抽象成本与收益对等**：
   - 仅服务单一局部场景的逻辑 → 保持局部实现
   - 确实多处复用 ≥ 3 个调用点 → 才安排沉淀公共模块
   - 抽象前后调用点写法对比，更复杂就不抽象

4. **避免抽象碎片化**：多个文件各自实现"用户信息获取的不同版本"是失败的抽象，应合并到同一 service。

5. **避免过早抽象**：第一次出现需求时不要急于做通用，等真的出现第二处第三处再抽。

## 派发上下文模板（task-build 必填）

写代码任务派发给子代理时必须包含以下字段：

```yaml
复用扫描:
  L1 直接复用:
    - <path:line> <name>  # 列出本次实施会调用的现有实现；如无写"无"
  L2 族成员:
    - <path:line> <name>  # 同领域已有；如无写"无"
    模式特征: <细粒度专用 / 通用参数化 / 混合 / 无统一模式>
  L3 项目模式:
    数据访问: <DAO细粒度 / 通用query / Repository / ORM 直用>
    组件层: <已有 Table/Form/Pagination 等 / 无通用组件库>
    业务层: <service / use-case / hook / 组件内>

复用决策:
  类型: <直接复用 / 遵循族模式 / 扩展现有 / 借机重构 / 确认新建>
  说明: <一句话为什么>
  影响调用点: <X 个 / 不影响>
  用户已确认: <是 / 否（低风险无需）>

实施约束:
  - 必须复用: <列出 L1 资产，不允许重新实现>
  - 沿用模式: <按 L3 模式实施，不引入新风格>
  - 禁止: <不允许的操作，如"不得提取公共抽象"、"不得改 DAO 模式"等>
```

## 写代理收到派发后的行为

子代理（code-full / code-fix / ui-designer）收到含上述字段的派发上下文后：

1. **核对必须复用项**：实施时必须调用 L1 列出的资产；不调用属违规
2. **遵循模式约束**：按 L3 给的模式风格实施
3. **报告复用清单**：完成时报告里必须含
   ```
   复用清单:
   - 复用: <path>（未改动）
   - 扩展: <path>（新增了 X，原 API 未改）
   - 新建: <path>（已确认无可复用，理由：<...>）
   ```
4. **派发缺该字段** → 报 `NEEDS-CONTEXT: 缺复用决策`，不要自己跑方法论

## 反模式（重点警示）

激活本 skill 时必须主动识别下列反模式：

❌ **重复造轮子**：项目已有 formatDate，又写 toDateString 做同样的事
❌ **抽象碎片化**：getUserA / getUserB / getUserC 散落多个文件做同一件事的不同版本
❌ **过早抽象**：第一次出现就提取通用方法，参数膨胀，调用方更复杂
❌ **粒度跳跃**：项目都是细粒度方法，新代码却混入一个 super-method(opts)
❌ **绕过现成**：不查就写，写完发现项目已有
❌ **拆得过散**：一个功能拆 8 个文件，每个 30 行，没有内聚意义

发现反模式 → 在派发决策中显式标注并给出修正建议。

## 与 reviewer 的边界

本 skill 服务的是**决策阶段**（task-build / planner）。

reviewer 不激活本 skill，它的职责是核对"实施是否遵循了派发上下文中的复用决策"——契约层判定，不重跑方法论，不质疑设计粒度选择本身。
